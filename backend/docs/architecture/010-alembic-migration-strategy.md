# Alembic Database Migration Strategy & Governance

## Overview
Database schema migrations are the version control mechanism for relational databases. As the VOLTA AI Chatbot evolves across domain models (`User`, `Ride`, `Conversation`, `Notification`, `SavedPlace`), database schema changes must be applied deterministically across development, staging, and production environments.

---

## 1. Why Database Migrations Are Necessary
- **Schema Version Control**: Tracks every table creation, column addition, index modification, and constraint change in Git.
- **Team Synchronization**: Enables multiple engineers to work concurrently without schema drift or manual DDL execution.
- **Deployment Safety**: Provides automated rollback mechanisms (`downgrade`) if a migration deployment encounters issues.

---

## 2. Naming Conventions & Constraint Governance
To prevent unpredictable constraint auto-names generated by database engines, all models inherit from `Base` configured with explicit SQLAlchemy `MetaData` naming conventions (`app/db/base.py`):

```python
POSTGRES_NAMING_CONVENTION = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

This guarantees deterministic naming across indexes (`ix_*`), unique constraints (`uq_*`), check constraints (`ck_*`), foreign keys (`fk_*`), and primary keys (`pk_*`).

## 4. Strict Project Governance Rules

### Rule 1: No Manual Production DDL
All database schema changes **must** be performed via Alembic migration scripts. Never execute raw `ALTER TABLE`, `CREATE TABLE`, or `DROP TABLE` statements manually against production or staging databases.

### Rule 2: Model Import & Auto-Registration Policy
`env.py` depends strictly on `Base.metadata`. Individual domain models should never be explicitly imported inside `env.py`. When domain models are introduced, they should be imported through a central module (for example `app.models`) so that `Base.metadata` contains all mapped models.

### Rule 3: No Placeholder Migrations
The initial migration file should only be created after the first domain models (`Chapter 2.4`) are defined. Do not commit empty or placeholder migration files to the repository.

## 5. Command Reference

| Command | Action | Description |
| :--- | :--- | :--- |
| `alembic revision --autogenerate -m "Create user table"` | Autogenerate Revision | Compares `Base.metadata` to active DB schema and writes version script |
| `alembic upgrade head` | Upgrade Schema | Applies all pending migrations up to the latest revision |
| `alembic downgrade -1` | Single Step Downgrade | Rolls back database schema by exactly one revision |
| `alembic current` | Display Head | Displays the active database schema revision ID |
| `alembic history` | Display Timeline | Lists all historical migration revisions chronologically |
| `alembic heads` | Display Revision Tree | Shows active head revisions across all migration branches |
| `alembic upgrade head --sql` | Offline SQL Generation | Generates DDL SQL script without executing against DB |

---

## 6. Future CI/CD Automated Pipeline Integration
In future automated deployment pipelines (GitHub Actions / GitLab CI), the release runner will automatically execute:

1. **Migration Upgrade**: `alembic upgrade head` (Applies schema updates to staging/production)
2. **Automated Test Execution**: `pytest` (Verifies system behavior against the updated schema)
