# ADR 014: ORM Relationship & Cascade Strategy

## Status
Accepted

## Date
2026-08-03

---

## Context
Defining domain entity models (`User`, `Conversation`, `Message`, `Memory`, `Intent`, `Entity`, `Recommendation`, `Booking`, `Notification`, `AuditLog`) requires a cohesive, production-grade strategy for managing ORM relationships, foreign key deletion cascades, query loading patterns, passive delete optimizations, and primary key identity.

---

## Technical Decisions & Rationale

### 1. Explicit `back_populates` Over Legacy `backref`
- **Decision**: All bidirectional ORM relationships explicitly declare `back_populates="..."` on both parent and child classes.
- **Rationale**: Eliminates implicit magic attributes generated by legacy `backref`. Guarantees clean static typing, IDE autocompletion, and explicit relationship boundary definition.

### 2. Async-Optimized Collection Loading (`lazy="selectin"`)
- **Decision**: All 1:N collection attributes (`User.conversations`, `Conversation.messages`, etc.) use `lazy="selectin"`.
- **Rationale**: `selectin` loading issues a targeted `IN (...)` secondary query when loading parent objects. This eliminates N+1 query performance traps while operating natively without blocking event loops in Async SQLAlchemy 2.0 environments.

### 3. Database Engine Deletion Optimization (`passive_deletes=True`)
- **Decision**: Relationships configured with database-level `ondelete="CASCADE"` or `ondelete="SET NULL"` set `passive_deletes=True`.
- **Rationale**: Directs SQLAlchemy to delegate foreign key cascades directly to the PostgreSQL engine rather than issuing redundant Python-side pre-fetch queries before executing DDL actions.

### 4. Financial & Transit Contract Protection (`Booking`)
- **Decision**: `Booking.recommendation_id` uses `ondelete="SET NULL"` with a nullable FK, while `Recommendation.bookings` omits orphan delete cascades.
- **Rationale**: A `Booking` record represents a real-world ride reservation / financial transaction. Ride booking records must **never** be implicitly purged if an AI `Recommendation` payload is removed.

### 5. Soft Delete vs Hard Delete Governance
- **Decision**: Standard operational deletions execute non-destructive soft deletion (`SoftDeleteMixin.soft_delete()`). Hard physical deletion (`DELETE FROM users`) is reserved for administrative purging or GDPR user data erasure requests.
- **Rationale**: Ensures historical dialogue analytics and audit trails remain preserved during standard application workflows while supporting compliance erasure requests when explicitly executed.

### 6. Immutable Audit Trail (`AuditLog`)
- **Decision**: `AuditLog` inherits ONLY `UUIDMixin`, `TimestampMixin`, and `Base`. It does NOT declare foreign key relationships or cascade deletion directives to actor users or resources.
- **Rationale**: Provides tamper-proof, immutable system audit history. Even if a user account or resource is permanently deleted or purged, historical `AuditLog` entries remain intact for legal and security auditing.

### 7. Native PostgreSQL UUID Primary Keys
- **Decision**: All domain models use native PostgreSQL `UUID(as_uuid=True)` primary keys defaulted to `uuid.uuid4`.
- **Rationale**: Prevents sequential primary key enumeration attacks on public API endpoints and allows distributed multi-region primary key generation without collision.
